# Usage Guide

[简体中文](USAGE.md) · English

This document describes current product behavior and does not imply that a public release is available. See the [Installation Guide](INSTALL.en.md) for installation status and platform limitations.

## Accounts and Files

Sign in with your own PikPak account. QR sign-in is selected by default: scan the code with the PikPak app and confirm on your phone to enter your drive. Refresh an expired code to try again. Adding accounts and reauthentication also support QR sign-in; when reauthenticating, select the matching account on your phone. QR codes contain temporary authorization information; do not publish screenshots or forward them.

If a confirmation request is already in progress when the QR countdown ends, the page waits for its final result: success completes sign-in; otherwise it offers a refresh. Closing the sign-in view or changing sign-in methods still cancels the flow.

You can switch to “Password.” Its “Remember account password” option saves your password in the system credential store, and “Auto sign-in” depends on it. Both are selected by default and can be deselected before signing in. QR sign-in needs no password and leaves an existing account’s remembered-password settings unchanged. The resulting session is still stored locally and renewed with a refresh token. A revoked session requires renewed authorization; existing password auto-sign-in preferences continue to apply.

Use the account entry in the lower-left corner to add, switch, and manage accounts; switching the account you are browsing does not stop local transfers already running for other accounts. Accounts are not merged into a single cloud drive. Signing out and removing an account clears the corresponding local session and records. It does not delete your PikPak account, delete its cloud files, or revoke its shares; cloud-add tasks may continue running on the server.

The Files page supports folder browsing, filtering by type, searching, starring, sharing, and previews, along with right-click context menus (for single items, multi-selection, and the folder canvas) and desktop keyboard shortcuts (`F2` to rename, arrow keys to move or `Shift` to extend selection, in-drive copy/cut/paste, and more; see “Settings → Shortcuts” for the full list). Building the initial local index may take some time. After you create a share, anyone who obtains the link or access code may be able to access the shared content. Configure sharing according to your actual needs and revoke shares promptly when they are no longer needed.

Right-click a single file or folder, or a multi-selection, and choose “Organize” to open the AI Assistant's media organization plan. One folder is planned with its subfolders; a selection is limited to the selected items. Local rules build the plan first; review and confirm it before execution. Opening the plan does not automatically call a model.

The file grid and filters adapt to the space available in the window. In short windows the workspace can scroll while the playback bar stays visible. This does not change system display scaling or reset your sidebar and information-panel choices.

In-app file and folder selection sheets share a grid/list switch, including move/copy, cloud sync folders, cleanup scope, Cloud Add destinations, Share Import, torrent files, and archive contents/extraction destinations. The grid uses thumbnails or type icons; the list emphasizes names and paths. Switching views changes presentation only: selections, account, location, and authorization scope remain unchanged, and nothing is submitted. Native system file/folder dialogs retain the system's own views.

### Batch File Operations

- Moves, copies, starring, Move to Trash, restore, permanent deletion, Cleanup, and download submissions appear in the bottom task strip while running. Successful results briefly remain before the strip hides. Reopen session history and per-item receipts from File tasks in the sidebar. Failed, unknown, or stopped receipts stay marked until each is viewed. Hiding the panel does not delete receipts; remove the current receipt from its details to delete that record. Continue selecting files or changing pages after submission.
- “Select all N loaded items” covers only loaded entries matching the current list filters, not unloaded results. Local search's “Select all results on this page” does not select the complete search catalog. Selecting a folder still includes its contents.
- File changes for one account run in submission order; other accounts and download submissions remain independent. Each queued task captures its original account, sources, and destination. File-page operations recheck names, locations, and the destination, refusing a source that changed rather than acting on a newer selection. Cleanup follows its scan results: a copy renamed or moved while queued is still processed as selected.
- Tasks distinguish queued, submitting, cloud processing, and result verification. Receipts distinguish success, known unapplied failures, unknown results, and unsent items. Only confirmed successes leave the original list; failures and newer selections are preserved.
- Retry individual or all known unapplied failures only after one confirmation of the original account, operation, and destination. Permanent deletion retains its irreversible-action warning. Timeouts, lost replies, and unconfirmed cloud results may already have applied and cannot be directly retried; inspect the actual result first.
- “Stop remaining submissions” cancels queued tasks or prevents later batches of an active task. Submitted operations still settle and are not rolled back. Ordinary file changes allow up to 5,000 items per task and 100 per batch. Empty Trash processes only the snapshot read at submission, excluding later arrivals while queued.
- A completed download receipt means submission to the existing transfer queue, not completed file bytes. A partially read or queued folder retains successful downloads and has an unknown result. View actual download progress in Transfers.
- The batch queue and receipts are window-session-only, not restored after quitting or reloading. Operations already accepted by the cloud may continue. Do not resubmit an uncertain operation just to discover whether it completed.


## Uploads, Downloads, and Cloud Add

- Use “New” to upload files, upload folders, or create a cloud folder. You can also drag local files onto the Files page.
- Choose “Download to computer” from a file’s More menu or the multi-selection action bar. The default location is the system Downloads directory, which can be changed under “Settings → Transfers.” Files with the same name are distinguished by numbering rather than directly overwriting existing files.
- Use “Cloud Add” in the top bar to submit links or torrents you are authorized to use. Task execution, availability, and quotas depend on the PikPak service.
- View progress in the “Transfer Center” and pause, resume, or retry tasks according to the operations each task supports. Quitting the application stops transfers on this computer but does not necessarily cancel cloud tasks.

### Open from a browser or this computer

- After installing the new PKP build, select it as the handler for `magnet:` links and `.torrent` files. Clicking a magnet link on a website or double-clicking a torrent starts PKP, or delivers it to the existing window when PKP is running.
- PKP opens the Cloud Add confirmation sheet; it never creates a task automatically. Magnets prefill the Links tab. Torrents are parsed locally so you can select files and confirm the current account and destination. This adds content to PikPak, not to a local BitTorrent downloader.
- Sign in or unlock first if necessary. The Links and Torrent tabs retain their inputs independently: an existing torrent does not block a new magnet from appearing on Links, and its file selection is preserved; opening a torrent also preserves existing links. Both tabs share the current destination. Requests of the same type wait in order behind that tab's unsubmitted input for the current run; submit or clear that input to continue. Requests wait while a torrent is being read or input is being submitted.
- To discard links, choose “Clear links” or edit/delete the text. “Cancel” discards the current tab's links or torrent and closes the sheet without changing the other tab or immediately opening the next request. The Close button or clicking outside the sheet still preserves drafts. Reopening Cloud Add or opening another external link/file resumes pending requests. Duplicate pending deliveries are coalesced so deleting input does not bring the same request back; deliberately reopening a discarded link still works. Quitting PKP does not persist unsubmitted requests.
- macOS: install the new `.app` in Applications and launch it once so the system discovers its handlers. For torrents, use Finder → Get Info → Open with → PKP → Change All. Magnet links follow the current system/browser protocol handler; PKP registration does not take over another app's existing default, so select PKP instead if necessary. Your browser may still ask for permission to open an external app.
- Windows: run the new installer, then choose PKP for `.torrent` and `MAGNET` under Settings → Apps → Default apps. Installation and uninstallation maintain PKP's candidate registrations without rewriting the user's default choices. Running a portable `.exe` alone does not register associations.

### Import a PikPak share

- Paste an `https://mypikpak.com/s/...` share into Cloud Add's Links tab, or into the main window outside input fields, to open Share Import. Packages also register `pkp://share?url=<URL-encoded complete HTTPS share URL>` for explicit website buttons or extensions. Ordinary HTTPS links still open in the browser; PKP does not take over HTTPS globally.
- Desktop builds can detect a copied share when PKP starts or its main window returns to the foreground, with another check once sign-in, unlock, and the account list are ready. A valid PikPak share opens preview without pasting. Existing dialogs and torrent reads/submissions are not interrupted. There is no background polling; unrelated clipboard text is not sent to the frontend, cloud APIs, or logs. Server builds never read their host's clipboard. Manual paste remains available if system access is denied.
- Canceling or closing prevents the unchanged clipboard share from reopening on repeated activation; explicitly opening another share does not undo that suppression. Copy a different valid share and return to detect it, or explicitly paste/open the original share again. Detection never starts a restore automatically.
- Enter an access code when required. Browse folders and pages in grid or list view with actual thumbnails and service-provided metadata; missing thumbnails use file-type icons, and selections can span folders. Single-click selects items; double-click opens folders or previews files (video and audio previews start playing automatically once loaded). Supported preview types include video, audio, images, PDF, and text, subject to encoding and available source resources.
- Choose the receiving account and an existing destination folder explicitly. Changing the receiving account rereads the share and clears its selections and destination without switching the account being browsed in the main window. The destination picker does not create cloud folders.
- Reading a share, loading thumbnails, and previewing content do not import it first. Only confirmation submits a restore. An accepted task is not yet complete: the sheet shows its processing state and offers to open the destination after completion.
- Cancel, Close, and clicking outside discard this share, access code, selections, and preview, and pause automatic presentation of the next request. Existing magnet/torrent drafts remain intact. A new external request or reopening Cloud Add can resume pending opens. Cold-start requests wait through sign-in, unlock, and receiving-account initialization.
- An accepted restore whose result is uncertain is not automatically resubmitted. Check the receiving account's destination first. Submission records protect against duplicates during the current run but are not persisted after quitting; restarting does not undo tasks already accepted by PikPak.

## Playback and Reading

Open a video or audio file to enter the built-in player. Depending on the file and service availability, you can switch quality levels, select subtitles, resume from your last playback position, or move playback to a separate window. Previews include text, images, PDF, DOCX, and XLSX. PPT/PPTX have no built-in preview; they remain classified as documents and show the existing unsupported-preview screen, with downloads and other operations unchanged. Network conditions, account permissions, server-side rate limits, and file encoding all affect playback; player failures may affect the entire application.

On macOS since v0.6.0, and on Windows x64/ARM64 since v0.6.1, choose Subtitles → AI subtitles, then Original, Chinese, English, Japanese, or Korean, even for a video without embedded subtitles. No model or API key under Settings → AI is needed: PikPak handles transcription and translation. Its server determines membership eligibility, available languages, time allowance, and the one-session-per-account restriction. Windows packages include the native audio decoder DLL; no separate FFmpeg installation is needed. Other platforms without an audio decoder hide the option. The published v0.6.0 Windows installer does not include this feature.

Membership checks use the account that owns the playing video, not the account being browsed. Nonmembers can still see the entry and reason, but cannot choose an AI language; Off and ordinary subtitles remain available. Failed membership reads can be retried without being labeled nonmembership, and rejected AI startup preserves the native subtitle.

The AI subtitle heading in the subtitle menu and the sidebar playback settings show remaining/total time and the reset time supplied by the server. These are the latest node/session snapshots, converted from seconds, not a local countdown. Before enabling or when no quota was returned, the UI says it will be retrieved after enabling rather than inventing zero. Off or failure retains the same account's latest snapshot; changing the playing account hides another account's quota. Quota is informative; the server still decides whether use is allowed.

Enabling sends the playing account's authorization, video GCID/file/media identifiers, and independently fetched and decoded audio near the playback position to the subtitle service. The extra media read consumes network traffic. Captions follow the video's timeline, seeking and pauses, and the existing subtitle style and delay controls. The choice carries into subsequent videos during this application run. Off, choosing a normal subtitle, or quitting ends the session; a refusal or disconnection turns it off with an explanation rather than reconnecting indefinitely. See [Privacy](../PRIVACY.en.md#optional-ai-and-tmdb) for processing and retention boundaries.

Quality changes re-resolve the audio actually selected, and rapid caption-language changes wait for the preceding session to release. Off or quit cancels subtitle-owned metadata and authentication requests or waits without interrupting another task's shared refresh. Failures appear on the player stage or in a notice while the player is collapsed; retrying and receiving the same error produces a new notice.

## LAN Sharing

LAN sharing is off by default and must be started manually after launching PKP. Set a separate, nonempty password and enter it twice; there is no minimum length or complexity requirement. Create a local-folder space or a space tied to a specific cloud account and root, then select a LAN interface and confirm. Devices on the same network can open the displayed address or scan its QR code. The QR code contains the address and current desktop language, never the password. First-time visitors inherit that language; a visitor's manually chosen language takes precedence. Opening the plain address uses the visitor's saved choice or browser language. Allow the connection through your system firewall. Router guest isolation may prevent devices from connecting. Do not configure public port forwarding.

When exactly one network interface is available, it is selected automatically; choose explicitly when several are available. Refreshing preserves a still-available choice and rechecks it if the interface disappears. Selecting an interface never starts sharing automatically.

The sharing service section provides “Prevent automatic sleep while sharing,” off by default and remembered locally. On supported macOS / Windows builds, enabling it requests prevention of idle system sleep only while sharing runs; the display may still turn off. Toggle it while sharing is running. Turning the option off, stopping sharing, an unexpected listener failure or quitting PKP releases the request. While stopped it stores only the preference, without holding a power request. Restarting PKP still requires starting sharing manually; the UI distinguishes enabled from actually active. System rejection reports failure rather than silently claiming protection.

This does not prevent manual sleep, lid-close sleep, shutdown, low-battery or system-forced sleep, nor guarantee Wi-Fi, network or external-disk availability. Connecting power is recommended and enabling it increases energy use. On battery-powered Windows Modern Standby systems, the OS may terminate these requests about five minutes after its sleep timeout. Desktop-initiated preparation can continue after sharing stops, but stopping sharing releases this option's protection; adjust system power settings yourself if preparation must continue. App lock and hiding the window do not stop active sharing, so they do not independently release enabled protection.

Desktop impact notices are acknowledged once per action type. After you select “I understand the access scope and consequences; do not ask again for this type of action” and the operation succeeds, this computer remembers the choice across restarts and spaces. Cancelling or a failed operation does not save acknowledgement. Later operations still require your click; nothing automatically starts sharing or expands permissions. Creating spaces and setting or resetting passwords retain their required forms without repeating an acknowledged checkbox.

To create a cloud space, choose its fixed source account and click folders to browse. Use the breadcrumbs or parent button to navigate. Select “Choose This Folder,” review the selected folder and full path, then create the space to authorize that folder. Choosing the cloud drive root includes every file in that account. “Change folder” reopens browsing; cancelling keeps the previous selection. Review the scope and submit after choosing a replacement; folder selection alone creates no space. Suggested space names follow folder changes unless you edit the name yourself.

The folder picker can search folder names across the selected source account's entire drive, showing full paths for up to 100 matches. Refine the query when there are many results. Search uses the existing local index; if it is not ready, clear the search and browse folder by folder. Clicking a result only navigates to that folder: you must still choose it and submit the new space. Clearing the search restores the previous browsing position, while switching accounts or closing the dialog discards stale search results.

The cloud-folder picker for a new shared space supports grid/list views and scrolls long folder lists internally instead of growing the entire dialog. In short windows the form remains scrollable and bottom confirmation actions stay visible. File preparation retains one content scroller for browsing and selected files. Long names and path summaries stay compact; click the selected path, or focus it and press Enter, to expand and review the full authorized scope, then activate it again to collapse it.

In a shared space, use Settings → Select files to prepare to browse only its authorized contents and select files across folders. Choose originals or compatible copies for common devices and explicitly confirm to submit them. This creates no sync pair and never uploads, deletes, or changes cloud files. Desktop preparation is independent of visitor preparation permission and does not enable it. Compatibility targets H.264/AAC/MP4; already compatible originals may be reused, while HDR or unsupported media may fail and individual devices still need verification. Partial submission failures remain listed for review and retry. Downloaded originals use the folder shown on the desktop tasks page; converted copies use the separate compatibility cache.

Supported originals play directly by default, without preparation prompts for a large index or automatically generated copies. For single-video, at-most-single-audio SDR MP4 files with an index above 4 MiB, choose More → Optimize startup (lossless) in the player to explicitly create a lossless playback copy. This repackages without re-encoding and leaves the original and its downloads unchanged. Initial preparation needs extra disk and complete validation; manually play the copy from its preparation page afterward. Opening from the library still prefers a supported original; an existing copy can be selected in file details. Dismissing optimization retains the original player. Multi-track, embedded-subtitle and HDR sources do not use this optimization.

On the desktop, LAN sharing → Storage & copies provides separate folders for prepared originals and compatible/lossless copies. Select an existing writable folder. Changes affect only future allocations; old originals and copies remain reusable in place and are never moved or deleted automatically. Wait for running preparation to finish or cancel it before changing folders; resuming already allocated held work retains its old path. A disconnected disk or replaced directory holds preparation instead of silently recreating it or choosing another location. Restore the disk and explicitly resume. Ordinary downloads and sync retain their own settings.

The picker defaults to list view; switch to the grid to see existing cloud image/video thumbnails and JPEG, PNG or GIF images already available on the computer. Files without a thumbnail, or outside preview format and size limits, use a type icon. Previewing never downloads a cloud original or starts preparation. Switching views or browsing other folders keeps the selection.

The picker marks original readiness and compatibility readiness for common devices separately. Files already ready for the current type cannot be selected again. Switching types preserves selections but skips files already ready for the newly chosen type when submitting. Compatibility is marked ready only when the current file version and result can be verified; otherwise the computer can recheck it when requested.

Directory loading uses matching list/grid skeletons and a loading indicator. Recently visited folders, thumbnails and each view's scroll position are cached only within the current picker, so returning and re-entering can reuse them. Use Refresh to reread the current folder. Closing the picker or switching shared spaces clears the cache; preparation still revalidates the source and permissions when confirmed.

Browsing and selected files share one scroller. The selected count in the fixed action area jumps to the selection list, without nested scrollbars for either small or large selections.

Cloud spaces still show existing cloud-download or two-way sync pairs covering the folder and link to their own settings. Preparation neither creates nor changes these pairs; completed originals are reusable after account, file and version checks. Existing pairs continue to run according to their own settings.

Add the visitor page to the Home Screen to open it in a dedicated window. The sign-in and shared-space home pages provide Add to Home Screen instructions; dismissing the card retains a text link, while standalone windows hide the prompt. On iPhone / iPad, use Safari → Share → Add to Home Screen and leave Open as Web App enabled when offered. Supported systems remove Safari browser bars, but do not bypass fullscreen, orientation-lock or PiP restrictions. Android / desktop browsers may offer installation or a shortcut in their menu; this HTTP LAN address does not guarantee full browser installation.

The Home Screen entry keeps the computer's current address; scan and add it again if the IP or port changes. A dedicated window may ask for the sharing password again. A disconnected page offers Reconnect and revalidates the session through a live request; stopping sharing, resetting the password and changing space authorization still revoke access as before. No Service Worker or offline-content cache is created, and file lists, videos, passwords and authorization responses are not saved for offline use. The computer must keep sharing on the same LAN. An offline cold launch cannot load this page; adding to the Home Screen does not encrypt HTTP traffic.

- Visitors can only read explicitly authorized folders, not upload, delete, or modify files. Local-folder shares exclude the internal `.pkp-sync` directory and its contents, and neither it nor a subdirectory can be selected as a shared root. Other hidden files may still be shared; use a dedicated folder. Symbolic links and directory junctions are not served. Cloud spaces retain their original account and root when you switch desktop accounts.
- Complete local originals can be downloaded directly. Cloud files first reuse completed desktop downloads or sync originals. Sync records must match the source account, file ID, and current cloud version, and verify actual contents rather than names or sizes alone. Otherwise prepare the file on the computer first, then choose Download original separately to transfer it to the visiting device. Initial large-file verification can take time. Completion never starts playback or a download automatically. Storage & copies shows the destination for new originals; existing resources may remain in previous folders. Local paths are not disclosed to visitors.
- Each space has its own preparation permission. Enabling it lets visitors consume the computer's network, disk, and processing resources. Identical requests reuse preparation work without cancelling independent desktop downloads. Visitors cannot create or control sync pairs. Completed, consistent originals remain reusable while sync is paused. Stopping sharing, resetting its password, or disabling a space does not pause, resume, or cancel sync, or delete completed sync originals. Compatibility copies still use their separate cache.
- Playback checks actual codecs and browser support. It prefers the original, then remuxing or audio-only conversion, and only converts video when necessary, at up to 1080p without stretching or upscaling. Originals are never overwritten, original downloads retain their bytes, and remuxing preserves video resolution. Compatibility copies must finish and pass validation before playback; streaming transcoding is not supported. Unsupported HDR conversion, subtitles, and extra tracks carry limitations; download the original for a local player when needed.
- The visitor library uses compact file rows with direct Play or Prepare actions. More actions provides file details and original downloads; phones select a shared space at the top and switch between files and computer preparation using the bottom navigation. Use the eye inside the password field to show or hide the login password.
- File rows prefer existing cloud image/video thumbnails, even before originals are downloaded to the computer. Without a cloud cover, ready local images can still produce thumbnails at up to 256px on the long side; other files retain type icons. Load near visible rows with at most two concurrent requests and 64 images in page memory. The computer revalidates the account, folder scope and version before serving bounded JPEGs; signed cloud URLs never reach visitors. Failures fall back to icons without downloading cloud originals or starting preparation. Refresh, navigation and sign-out clear the page cache. Browser-chrome or keyboard height changes no longer pull the list back.
- On phones, image preview fills the viewport. Navigate loaded, ready images in the same folder with previous/next buttons, horizontal swipes or arrow keys and a position counter. It never prepares cloud originals or preloads neighboring full images automatically. Navigation revalidates file access; return to the list to load more pages. The viewer and other dialogs lock the background list and restore its scroll position on close.
- Play, preview and details show an immediate waiting state. File verification and playback checks offer “Cancel waiting” so you can retry; this only stops the current browser read, not submitted preparation tasks. Initial original verification or media probing can still take time, without invented progress percentages. Failures release the controls for another attempt.
- The optional system-decoder query waits at most 250ms, then attempts playback using exact browser codec support without automatic conversion. Media metadata is reused only for the same version and local file identity. First reuse of downloaded or synced cloud originals still verifies complete content; slow disks or cloud responses can still delay startup.
- Initial playback shows a centered loading indicator until a usable frame is available. Later data shortages show buffering, which clears as presented frames advance without requiring another playing event. Audio and browsers without frame callbacks recover from actual playback-time progress; metadata and seek jumps do not count as resumed playback. Pause, browser gesture requirements and failures show their own states without invented percentages. Cloud byte-range requests can batch-check known ancestor IDs, but fetch fresh authorization metadata every time; moved or revoked files cannot reuse old paths.
- Cloud folders show the first 100 entries, then fetch more near the list bottom or with “Load more files.” Search continues through the remaining pages and shows its incomplete state; failed pages require explicit retry rather than repeated automatic requests. Local folders are read together. Browsing snapshots stay only in this page, bounded to 12 folders / 20,000 entries. Returning shows the snapshot immediately and revalidates it; the visible page is checked about every 30 seconds. Refresh starts again from the first page. File actions and content requests always recheck authorization and versions; browsing snapshots never grant access.
- During a slow read, another folder or file can be selected immediately, cancelling the abandoned request. Submitted preparation and other writes still reject duplicate operations. Background pages pause unnecessary status refreshes, and task views request their needed state. Initial media probing, complete-original verification and cloud-service latency cannot be skipped.
- Computer preparation supports “Delete record” and “Clear finished records” for completed, failed, or cancelled records in the current space. Cancel active or held requests first. Cleanup only changes this visitor session's list and survives page refresh; it does not affect other visitors, desktop tasks, originals, or compatible copies. Signing out or session expiry followed by a new sign-in shows the shared history again.
- The desktop LAN Sharing → Preparation tasks page also supports removing one record or clearing finished records in the selected task scope. “All spaces” includes history from removed spaces. Cleanup only hides the desktop list across restarts; visitor lists, source files, downloaded originals and compatible copies stay unchanged. Cancel active or held tasks first; requesting preparation again or retrying makes the relevant record visible again.
- Desktop preparation uses compact rows with internal scrolling for long lists. Desktop and visitor progress transition between actual readings and show a percentage only when a total can be calculated. Pauses and stage changes appear immediately; unknown totals are not estimated.
- The web player uses a compact two-row dock: time and timeline above, with playback, ten-second skips, speed and fullscreen below. Narrow screens keep brightness, mute and picture-in-picture in More; supported normal portrait playback also has a header PiP shortcut. Normal portrait places the always-visible dock below the video without covering it; landscape or fullscreen overlays the dock with auto-hide and tap-to-reveal. Mobile fullscreen requests a browser landscape lock; if unavailable or blocked by orientation settings, only the player surface rotates into landscape without changing system direction. Gestures, seeking and menus use displayed-picture coordinates after rotation. Exiting releases this player's orientation lock and restores the layout, scroll position and previous playlist visibility without reloading the video. Playback always hides the shared-page header and search. Default fullscreen retains custom controls, so Safari browser bars may remain visible; supported devices offer More → System fullscreen (Safari controls) as an explicit switch to native video fullscreen without browser bars, using Safari controls. Back, Escape or browser Back leaves fullscreen first, then returns to the same folder, search and scroll position.
- Mobile gestures include horizontal seek preview committed on release, vertical swipes on the left for picture brightness and on the right for controllable web volume. Brightness only dims this video, never the system display; unsupported volume shows a device-button prompt, not a fake percentage. Tap to show/hide floating controls, double-tap either side to skip ten seconds, or the center to play/pause. Buttons, the timeline and brightness slider remain available. Multi-touch, cancellation and screen-edge navigation do not commit seeks. Portrait and landscape preserve the full video frame and safe areas, with auto-hide in landscape or fullscreen playback. More → Playback gestures explains these controls. Desktop keys: Space/K play/pause, Left/Right seek, Up/Down adjust supported volume, M mute and F fullscreen. Editing fields and menus retain native keys.
- Swipes and ten-second skips use lightweight translucent feedback. Loading/buffering overlays wait until that feedback ends and appear only while data is still needed; errors and play-gesture prompts take priority. Dragging the timeline previews a position while temporarily pausing, commits one seek on release, and restores the previous playing/paused state only when the target frame is available. Cancelling does not seek. Buttons, keys and picture gestures likewise wait for the selected target before continuing rather than playing intermediate positions.
- On supported phones, the portrait header PiP shortcut or More → Picture in picture opens the current video in a system floating window. Choose it again or close the system window to leave, without reloading the source or changing playing/paused state. Entering from custom page fullscreen restores the page layout. Where available, actual ownership from the standard PiP API determines entry/exit state; only older Safari uses video presentation mode. Returning to the page or reopening More refreshes the state to avoid a stale Exit picture in picture label. Unavailable devices/browsers hide the entry. System settings, page permissions or the video can still reject a request; restrictions are not bypassed.
- Player menus share fixed icon dimensions and one text alignment column. Playback gestures, brightness, More and speed popovers close when clicking outside, while their contents remain readable and interactive. A tap on the picture used to dismiss a popover does not also pause or trigger picture gestures. The opener and Escape still close popovers.
- The player's folder list starts with the current file and an initial chunk. Each “Load more files” action appends up to 50 entries without recycling already shown rows during scrolling; every file remains reachable.
- Compatible and lossless copies have no fixed storage quota. Preparation is bounded by the selected disk's actual free space, retaining at least 512 MiB plus conversion-finalization headroom. Insufficient space stops preparation without automatically deleting existing copies for a new task. Storage & copies shows used space or “No compatible copies,” with cleanup disabled when empty. Explicit cleanup skips active readers and preparation work and never deletes originals or other downloads.
- Stopping sharing or resetting its password revokes visitor sessions and interrupts downloads and playback; disabling a space interrupts its access. Files already obtained cannot be recalled. Visitor-only preparation may finish its current safe stage and then waits for renewed authorization, while preparation initiated or adopted by the computer continues. Disabling a space holds both; cancel the desktop task to stop it immediately.
- Source verification may need to wait for the cloud service. Preparation held because its source is unavailable does not retry automatically. Once the account, network, and authorized folder are available again, choose “Prepare again” in the visitor preparation details and confirm against the current source and permissions, or choose “Resume preparation” on the desktop. Visitors can cancel their own interest even when the file is temporarily unavailable; preparation continues if other visitors still need it. Stopping sharing, resetting its password, and disabling spaces still revoke visitor access directly.

**Plain HTTP does not encrypt passwords or file contents. Use only on a trusted LAN. App lock and window hiding do not stop sharing; stop it explicitly or quit PKP.** Sleep, network changes, or unavailable source folders/accounts can interrupt access. The visitor page supports Simplified Chinese, Traditional Chinese, English, Japanese, and Korean.

## Folder Sync and Organization

“Sync” lets you create relationships for two-way sync, local-to-cloud backup, or cloud-to-local download. Confirm the directories on both ends and the mode first, then review the scan preview before proceeding. Content verification may read cloud file bytes and consume download traffic. Sync is neither a real-time service nor a system-level background daemon; it works only while the PKP process is running.

## Settings and Quitting

Before signing in, open Privacy from the login page to turn off Send anonymous usage statistics in local settings. You can also switch to About & Updates there; neither requires a PikPak sign-in.

“Settings” lets you adjust the language, appearance, transfers, the application’s own network proxy, privacy and security, and other options. Proxy settings do not modify the system VPN or system proxy. On macOS 12/13, WebView image loading does not support the same proxy configuration as the application and may still connect directly.

On macOS, closing the main window only hides it; menu bar residency and background transfers for each account may continue. Use “Quit PKP” or `⌘Q` to fully quit. App lock is disabled by default. Locking does not stop already authorized background transfers or sync, nor does it encrypt downloaded files or the entire local data directory.
The standalone App Lock password also has no minimum length or complexity requirement: enter a nonempty password twice when setting or changing it. Short passwords are easier to guess. Both password types retain their existing input-size limits and failed-attempt throttling.

Before reporting an issue, redact account information, filenames, paths, share links, tokens, and API keys. Do not upload the entire configuration directory or raw logs.
