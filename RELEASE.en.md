# Release Boundaries

[简体中文](RELEASE.md) · English

This file describes only the release constraints for the public repository. It does not record private keys, local machine identities, or historical run IDs.

- The source module is `github.com/tonyflux/pkp`. The product name, `com.pkp.desktop`, configuration directory, and installation location remain unchanged.
- PKP's own source code is licensed under GPL-3.0-only. The released v0.1.0 installation packages are governed by `docs/legal/v0.1.0-proprietary.txt`; do not retroactively apply the current source code or the new license to that version.
- Starting with v0.2.0, releases contain eight attachments: two installation packages, `update.json`, `update.json.sig`, `PKP-<version>-source.tar.gz`, `libmpv-sources.tar.gz`, `LICENSE`, and `SHA256SUMS`. The PKP source archive corresponds to the commit used for this build. Installation packages must not be committed to Git. The seven historical v0.1.0 attachments remain unchanged.
- Keep the update-signing private key outside the repository or in the optional protected GitHub `release` environment, never in ordinary CI. If it is lost, do not silently replace the public key trusted by distributed clients.
- The maintainer has confirmed that the current third-party client identity parameters may be published and reused. Authentication values, the signing algorithm, and referral behavior remain unchanged. This does not imply PikPak endorsement or an independent legal audit.
- The maintainer has confirmed permission to publish and distribute the current application mark with the open-source source and installation packages; it is no longer an unresolved blocker. This does not imply official endorsement. See `docs/legal/artwork-provenance.md` for provenance and export-chain boundaries.
- From v0.2.0, macOS uses an explicit “Download Update → Restart & Update” flow. After preparation and user-confirmed quitting, the helper replaces the app in place and reopens the same profile, preserving accounts and settings. macOS may request replacement permission; other PKP instances using the same app must quit first and are not forcibly terminated. The existing stable `update.json`, Ed25519 signature, DMG, and embedded trust key remain in use. There is no Sparkle, automatic download, silent installation, quarantine removal, or Gatekeeper bypass. Released macOS v0.1.0 still requires one manual drag replacement to gain this feature. Windows keeps its existing user-confirmed quit-and-run-installer flow.
- Isolated, signed, windowless native fixtures have exercised cancellation, integrity rejection, instance contention, replacement with same-profile relaunch, and rollback after launch failure; see the reproducible scripts in the [development guide](docs/DEVELOPMENT.en.md). Before official release, manually verify the real app's quit confirmation, system replacement authorization approval/cancellation, Gatekeeper, and upgrades across supported devices. Isolated smoke tests are not production-upgrade acceptance, and update signatures are not Apple signing or notarization.

## Release paths

Version 0.2.0 was the first open-source release; v0.3.0 retains the eight assets above and the existing update trust key. macOS remains ad hoc signed and not notarized; Windows has no Authenticode signature and remains preview support, with incomplete device acceptance. Built-in PPT/PPTX previews and `pptx-preview` have been removed, so that dependency no longer blocks the current source; this does not retroactively resolve historical distribution obligations. The maintainer has confirmed distribution permission for the current application mark; see [third-party notices](THIRD_PARTY.en.md) for other asset and provenance boundaries. Review both release notes and complete platform acceptance before official publication; native Windows installation and upgrade still await manual verification. The signing key must match the public key embedded in existing clients, which the release tool checks. Never commit the key or change the trust key silently.

Commit the intended source, assets, dependency locks and release notes as a clean snapshot before packaging. `make release-local` captures HEAD before building and confirms that source has not changed when archiving. It rejects uncommitted or nonignored untracked files, tracked caches, submodules and Git attributes that transform archive content. The signed manifest records the source commit, tree, archive size and hash. Upload requires that actual source commit to exist in public `main` history; an old documentation-only commit cannot substitute. The source archive includes pinned Go/npm inputs and isolated cache restoration instructions; media sources are attached separately. See [THIRD_PARTY.en.md](THIRD_PARTY.en.md) for the material boundaries.

- **Local:** On macOS, install the build prerequisites described in the development guide, including Wails, CMake, NSIS and the tools needed for the bundled libraries. Run `make release-local RELEASE_NOTES=build/release-notes.md RELEASE_KEY=/secure/path/to/update-ed25519.key`, then `make release-verify`. This builds and signs locally without uploading. To upload the verified draft, authenticate `gh` with permission to publish to `tonyflux/pkp`, then run `make release-draft`; after review, `make release-publish` promotes it as Latest.
- **Optional GitHub workflow:** Configure the `release` environment externally with appropriate required reviewers and deployment restrictions, and environment secrets `UPDATE_SIGNING_KEY` (the matching private key) and `PUBLIC_RELEASE_TOKEN` (permission to publish releases to `tonyflux/pkp`). GitHub environment protection is a repository setting, not enforced by this file; do not configure these secrets for pull-request CI. A pushed stable tag runs checks and, after environment approval, builds, signs, verifies and uploads a draft. Alternatively dispatch the workflow from `main` with an existing tag and `publish` false. After reviewing the draft, dispatch from `main` with that tag and `publish` true; the workflow downloads and verifies the existing draft before promoting it without rebuilding. The tag must match the source version and point to a commit reachable from `main`. Protect tag creation and workflow changes separately.

Neither path publishes merely by preparing these files. Verify the eight attachments, corresponding source, signatures, and hashes, and perform the post-release public download check when a release is actually published.
