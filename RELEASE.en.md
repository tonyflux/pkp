# Release Boundaries

[简体中文](RELEASE.md) · English

This file describes only the release constraints for the public repository. It does not record private keys, local machine identities, or historical run IDs.

- The source module is `github.com/tonyflux/pkp`. The product name, `com.pkp.desktop`, configuration directory, and installation location remain unchanged.
- PKP's own source code is licensed under GPL-3.0-only. The released v0.1.0 installation packages are governed by `docs/legal/v0.1.0-proprietary.txt`; do not retroactively apply the current source code or the new license to that version.
- Historical eight-asset releases from v0.2.0 remain verifiable. New releases add a per-user Windows installer authenticated by `windowsUserPackage`; `packages` retains the two legacy macOS and machine-wide Windows entries. Linux-inclusive releases additionally include amd64/arm64 deb, rpm, AppImage and corresponding-runtime-source archives authenticated by `linuxPackages`. PKP-owned source corresponds to the release commit; Linux runtime source matches the distribution packages actually bundled, not the macOS/Windows media-source archive. Do not commit installers; historical v0.1.0 terms remain unchanged.
- Keep the update-signing private key outside the repository or in the optional protected GitHub `release` environment, never in ordinary CI. If it is lost, do not silently replace the public key trusted by distributed clients.
- The maintainer has confirmed that the current third-party client identity parameters may be published and reused; authentication values and the signing algorithm remain, while automatic post-sign-in referral submission and registration attribution have been removed from the current source (previously established relationships are not automatically revoked). This does not imply PikPak endorsement or an independent legal audit.
- The maintainer has confirmed permission to publish and distribute the current application mark with the open-source source and installation packages; it is no longer an unresolved blocker. This does not imply official endorsement. See `docs/legal/artwork-provenance.md` for provenance and export-chain boundaries.
- From v0.2.0, macOS uses an explicit “Download Update → Restart & Update” flow. After preparation and user-confirmed quitting, the helper replaces the app in place and reopens the same profile, preserving accounts and settings. macOS may request replacement permission; other PKP instances using the same app must quit first and are not forcibly terminated. The existing stable `update.json`, Ed25519 signature, DMG, and embedded trust key remain in use. There is no Sparkle, background automatic download or installation, quarantine removal, or Gatekeeper bypass. Released macOS v0.1.0 still requires one manual drag replacement. Windows selects the installer matching its installation scope; signed `installProtocol: 1` packages update and restart after confirmation, while older protocols retain the installer wizard.
- Isolated, signed, windowless native fixtures have exercised cancellation, integrity rejection, instance contention, replacement with same-profile relaunch, and rollback after launch failure; see the reproducible scripts in the [development guide](docs/DEVELOPMENT.en.md). Before official release, manually verify the real app's quit confirmation, system replacement authorization approval/cancellation, Gatekeeper, and upgrades across supported devices. Isolated smoke tests are not production-upgrade acceptance, and update signatures are not Apple signing or notarization.
- Linux verifies signatures and hashes before revealing a download for explicit package-manager installation or manual AppImage replacement after quitting. It does not elevate or overwrite system files. Ubuntu 24.04 with GTK4/WebKitGTK 6.0 is the build baseline. AppImage retains the WebKit sandbox and requires kernel user namespaces. Describe Secret Service, polkit policy/agents, tray-host availability and screenshot-protection limits truthfully.

## Release paths

Version 0.2.0 was the first open-source release; historical two-platform releases retain the eight-asset set above and the existing update trust key. New releases add the per-user Windows installer; Linux-inclusive releases add the eight Linux assets described above. macOS remains ad hoc signed and not notarized; Windows has no Authenticode signature and remains preview support, with incomplete device acceptance. Built-in PPT/PPTX previews and `pptx-preview` have been removed, so that dependency no longer blocks the current source; this does not retroactively resolve historical distribution obligations. The maintainer has confirmed distribution permission for the current application mark; see [third-party notices](THIRD_PARTY.en.md) for other asset and provenance boundaries. Review both release notes and complete platform acceptance before official publication; native Windows installation and upgrade still await manual verification. The signing key must match the public key embedded in existing clients, which the release tool checks. Never commit the key or change the trust key silently.

Commit the intended source, assets, dependency locks and release notes as a clean snapshot before packaging. `make release-local` captures HEAD before building and confirms that source has not changed when archiving. It rejects uncommitted or nonignored untracked files, tracked caches, submodules and Git attributes that transform archive content. The signed manifest records the source commit, tree, archive size and hash. Upload requires that actual source commit to exist in public `main` history; an old documentation-only commit cannot substitute. The source archive includes pinned Go/npm inputs and isolated cache restoration instructions; media sources are attached separately. See [THIRD_PARTY.en.md](THIRD_PARTY.en.md) for the material boundaries.

Before freezing source, run `go mod download all` and commit the completed `go.sum` with the other release inputs. Corresponding-source export uses the complete dependency graph; do not let it add checksums after the snapshot is frozen or bypass the clean-snapshot check.

Ordinary CI and signed builds share the `media-…` cache keyed by OS, architecture and media-build script contents; misses still rebuild from pinned, SHA-256-verified sources. CI checks the complete Go dependency lock during frontend checks, and signed builds repeat the check before packaging. Signing keys are not cached; native tests, updater smoke checks, source consistency and release verification remain required.

- **Local:** Install macOS Wails/CMake/NSIS/native-media prerequisites and first build both Linux architectures and their provenance files from the same clean snapshot (see the [development guide](docs/DEVELOPMENT.en.md)). Run `make release-local RELEASE_NOTES=build/release-notes.md RELEASE_KEY=/secure/path/to/update-ed25519.key LINUX_RELEASE_DIR=/path/to/Linux/assets`, then `make release-verify`. Signing checks source revision and asset hashes; provenance files are not published. This prevents accidental reuse of stale packages, not deliberate forgery of the build or provenance. Omitting `LINUX_RELEASE_DIR` builds macOS and both Windows installers, without Linux assets. Building/signing does not upload; use `make release-draft` and `make release-publish` after review.
- **Optional GitHub workflow:** Configure the `release` environment externally with appropriate required reviewers and deployment restrictions, and environment secrets `UPDATE_SIGNING_KEY` (the matching private key) and `PUBLIC_RELEASE_TOKEN` (permission to publish releases to `tonyflux/pkp`). GitHub environment protection is a repository setting, not enforced by this file; do not configure these secrets for pull-request CI. Release builds run only by explicit dispatch from `main`: specify an existing source tag and set `publish` to false to run checks and, after environment approval, build, sign, verify and upload a draft. Pushing a tag does not start a release build; after local publication, the independent `release-check.yml` still verifies public assets on `release.published`. Main-branch and pull-request CI remain unchanged. After reviewing the draft, dispatch from `main` with that tag and `publish` true; the workflow downloads and verifies the existing draft before promoting it without rebuilding. The tag must match the source version and point to a commit reachable from `main`. Never rebuild, re-sign or overwrite an already published version; publish a new version instead. Protect tag creation and workflow changes separately.

Preparing these files does not publish a release. Verify the complete signed asset set, corresponding sources, signature and hashes, then perform the public-download check. Both Linux CI architectures must build the same source tag and are collected during signing; never mix artifacts from different commits.
